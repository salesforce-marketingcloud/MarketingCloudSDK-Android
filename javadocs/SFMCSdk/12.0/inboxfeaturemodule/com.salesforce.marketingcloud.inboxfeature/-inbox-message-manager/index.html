InboxMessageManager

interface InboxMessageManager

Reads and manages Inbox messages, from both Marketing Cloud servers (MCE and MAM). Get the instance from InboxFeature.getInboxMessageManager; configure the feature with com.salesforce.marketingcloud.inboxfeature.config.InboxFeatureConfig.

A message is active from its start date until its end date, if it has one. The query and count methods only see active messages. MAM messages are scoped to the currently identified user (or to the anonymous user when none is set); MCE messages are shared by all users of the device.

Threading: the query and count methods (getMessages, getUnreadMessages, getReadMessages, getDeletedMessages and the get*Count methods) read and decrypt the local database synchronously on the calling thread, so they are annotated WorkerThread: call them off the main thread, e.g. withContext(Dispatchers.IO) { manager.getMessages() }, and post the result to the UI. The mutations and track methods only queue their work on an SDK background thread, and every listener is called on the main thread.

While Inbox is disabled (isInboxEnabled is false: blocked by privacy mode, disableInbox, or disabled in the config) the query methods return an empty list, the count methods return 0, the mutations and track methods are ignored (logged), and refreshInbox is refused. Registered listeners are kept but not called; the first fetch after Inbox is enabled again notifies them.

refreshInbox
Link copied to clipboard
abstract fun refreshInbox(listener: InboxMessageManager.InboxRefreshListener?)

Requests an updated list of Inbox messages from Marketing Cloud. listener, if provided, is notified at most once per source for this call: once for each configured server (MCE, MAM) whose fetch completes, tagged with that server. Once the first server answers, a new refresh may be started; doing so stops this listener from receiving the remaining server's outcome. Outcomes are not matched to a specific call: a server's next outcome goes to the latest refresh's listener, even if it comes from a fetch started earlier. If the module itself refuses or cancels the request (a refresh is already in progress, Inbox is disabled or GDPR-blocked, or Inbox is disabled/torn down before any server has answered), listener is notified once with (false, Event.Producer.INBOX_FEATURE_MODULE). If Inbox is disabled/torn down after one server has answered, listener is released without a callback for the other server. Every listener callback, including a refusal, is made on the main thread after this call returns.
